fixes a lost back-sector DDR pointer tag. Earlier renderer/walking FPS figures
below under-rendered open portals and must not be used for the corrected

This harness tests native 8051 arithmetic and the original DDR draw fixture.

## Arithmetic

`fw/doom/fixed_math.asm` is generated by `scripts/doom_math_gen.py`. It contains
standard MCS-51 instructions selected using `dw8051_model.json` cycle costs.

- `_DoomFixedMul`: exact signed product bits 16..47, with carries from the
  discarded low columns. Unrolled Comba accumulation uses rotating register
  roles, keeping one operand in registers. Fifteen hardware `MUL AB`s normally;
  seven when either 16.16 operand is integral. Zero integral operand exits early.
- `_DoomFixedDiv`: signed `(a * 65536) / b`, truncating toward zero, with Doom's
  conservative `(abs(a) >> 14) >= abs(b)` saturation guard. INT_MIN and zero
  divisor are handled without C signed-overflow/abs undefined behaviour.
  Separate 8/16/32-bit remainder paths; skips zero quotient bytes (16/24/32
  bit steps), uses a hardware `DIV AB` quotient byte when its initial remainder
  is zero, and uses `ADD A,Rn` to avoid a carry-clear per shift step.

Internal register ABI: signed a in R4..R7, b in R0..R3, MSB first; result in
R4..R7. All eight registers, A/B/flags and 15 allocated DATA bytes are clobbered.
Non-reentrant. All four register banks were tested. This matches the register
layout used by compiler long-arithmetic helpers, **not an ordinary two-long C
function declaration**. `fixed_abi.asm` supplies a standard non-reentrant SDCC
ABI-zero wrapper; `fixed_stack_abi.asm` supplies the stack-auto version.
Code-bank call/trampoline overhead is not included in these helper timings.

## Recorded results

225,309 input pairs for EACH function, zero mismatches: edge-value cross-product,
seeded full-width values, Doom-sized values, non-saturating 8/16-bit divisors,
integral operands and values immediately around saturation thresholds.
Python arbitrary-precision arithmetic is the independent oracle; the candidate
math executes as actual opcodes on the DDC DW8051 fast core, without math stubs.

| Path | Median CPU clocks | At 350.791 MHz |
|---|---:|---:|
| Fractional multiply | 1256 | 3.580 us |
| Integral-operand multiply | 660 | 1.881 us |
| Division, whole specified test mix | 5396 | 15.382 us |

These are simulator results, including the existing SPI cache/fetch model
(116.9 MHz flash, 3:1 CPU/flash ratio). Cache geometry remains an assumption in
that model. The corpus is a correctness/workload sample, not a Doom profile.
No claim that these are globally fastest possible implementations is made.

## DDR and output

The native [DDR interface](sim-ddr.md) supplies 32 MiB separately from XDATA.
`tests/ddr_sim_fw.c` includes the existing `fw/test/ddr_draw.c` unchanged, builds
an 8051 firmware image, draws the grid/circle and writes/verifies address data
in the final 8 KiB of DDR. It runs on the same fast core:

- 1,605 writes and 512 verified read bursts, zero mismatches/hazards/stack wraps.
- With every seventh ready flag suppressed: 597 reads, 85 injected drops, all
  512 bursts eventually verified; stack high-water 154, zero wraps.
- The harness AwtoMs counter is only a timeout bound, not a performance clock.
- DDR command latency is ideal by default; no hardware FPS follows from this.

The image comes from **actual simulated DDR bytes written by the firmware**.
`sim_live.py` can capture that raster through its existing MJPEG/VLC endpoint:

```sh
python scripts/sim_live.py IMAGE.bin IMAGE.map --ddr 160x100 --port 8099
vlc http://127.0.0.1:8099/stream
```

For UHD block 1 (chip A = even screen rows; odd rows are chip B, awto-ddc#348) use
`--ddr 3840x1080 --ddr-line-repeat 2` (stretched view).
`--ddr-base` and `--ddr-pitch` specify byte addresses/strides. This deliberately
does not model scaler scanout, HDMI capture, scaling or double/triple buffering.

## Reproduce

Requires Python (numpy, Pillow, pytest), gcc, SDCC assembler/linker/compiler and
the large-stack-auto support libraries. FFmpeg is needed for MP4 capture.
The firmware fixture was built with Debian SDCC 4.5.0 #15242 in this run.

```sh
python scripts/doom_math_gen.py
python scripts/doom_sim.py --sdcc /path/to/bin/sdcc \
  --libdir /path/to/share/sdcc/lib/large-stack-auto \
  --math-vectors 100000 --capture-stream
python scripts/fastcore_check.py timing
AWTO_SDCC_BIN=/path/to/bin python -m pytest -q \
  tests/test_sim_ddr.py tests/test_doom_math.py tests/test_sim_idle_irq.py \
  tests/test_ddr_draw_host.py tests/test_ddr_addr.py
```

The last command requires `AWTO_SDCC_BIN` so the math test runs rather than
skips. `--capture-stream` starts the actual MJPEG HTTP handler, checks its JPEG
endpoint, records one second from `/stream` with FFmpeg and stops the server.
`--serve 8099` instead leaves the capture endpoint available until interrupted.
Results, Intel HEX/map files, PNGs and the MP4 are in `tmp/doom-sim/`.

The timing check initially found an existing fixture mismatch: its Cells mock
lacked the instruction stamp now required by ClockModel. The mock now supplies
`instr = 0`; all 297 opcode/stretch cases, timers, dual DPTR and clock formulas pass.
